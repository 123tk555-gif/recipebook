# 本番運用の手順

公開用のサーバー(AWS EC2、メモリ 1GB)で、レシピ管理アプリを動かすための手順です。
サーバーの作成と公開(EC2・ドメイン・HTTPS)は別の手順書にまとめます。ここでは、そのサーバーの上での設定と運用を扱います。

## 構成

```
[ブラウザ] ──HTTPS──▶ [Caddy](証明書を自動で取得)──▶ [Rails(Puma)]──▶ [MySQL 9.7]
                                                         │ ジョブ(Solid Queue)も Puma の中で動く
                                                         └─ 画像は storage ボリュームに保存
```

`compose.prod.yaml` に3つのコンテナ(`db`・`app`・`caddy`)をまとめています。データベースは外に公開しません。

### メモリの実測(このPCで本番と同じ構成を動かし、ページを160回開いたあと)

| コンテナ | 使用量 | 工夫 |
|---|---|---|
| MySQL | 142MB | バッファーを 64MB に、performance_schema を止める(初期設定のままだと 496MB) |
| Rails | 151MB | Puma は1プロセス・3スレッド。ジョブも同じプロセスのスレッドで動かす(別プロセスにすると 288MB) |
| Caddy | 14MB | |
| 合計 | 約 310MB | 1GB のサーバーで、OS の分を足しても余裕がある |

## 最初の設定(.env)

`.env.example` をコピーして `.env` を作り、値を書き換えます。`.env` は git に入れません。

```sh
cp .env.example .env
openssl rand -hex 24   # DB_ROOT_PASSWORD 用(DB_PASSWORD 用にもう1回)
openssl rand -hex 64   # SECRET_KEY_BASE 用
```

- `APP_HOST` と `SITE_ADDRESS` は、公開するドメイン(例: `52-194-241-136.sslip.io`)にします
- Rails の秘密鍵は `SECRET_KEY_BASE` で渡すので、`config/master.key` をサーバーに置く必要はありません

起動・停止:

```sh
docker compose -f compose.prod.yaml up -d --build   # 起動(初回はイメージを作るので数分かかる)
docker compose -f compose.prod.yaml logs -f app     # ログを見る
docker compose -f compose.prod.yaml down            # 止める(データは残る)
docker compose -f compose.prod.yaml exec app bin/rails "admin:grant[メールアドレス]"   # 管理者を決める
```

## メール(Amazon SES)

パスワード再設定のメールを送るために使います。設定しないと、メールは送られません(アプリは動きます)。

1. **送信元の認証**: SES の画面(東京リージョン)の「ID(Identities)」で、送信元のメールアドレス(またはドメイン)を登録し、届いたメールのリンクで認証する
2. **SMTP 認証情報を作る**: SES の「SMTP 設定」から「SMTP 認証情報を作成」。表示されたユーザー名とパスワードを控える(IAM のアクセスキーとは別物。パスワードはこのときしか表示されない)
3. **.env に書く**:
   ```
   SMTP_ADDRESS=email-smtp.ap-northeast-1.amazonaws.com
   SMTP_PORT=587
   SMTP_USERNAME=(2 のユーザー名)
   SMTP_PASSWORD=(2 のパスワード)
   MAIL_FROM=(1 で認証したアドレス)
   ```
4. `docker compose -f compose.prod.yaml up -d` で反映する
5. **サンドボックスの解除**: 作ったばかりの SES は「サンドボックス」で、認証したアドレスにしか送れない。誰にでも送れるよう、SES の画面の「本番稼働アクセスをリクエスト」から申請する(用途: パスワード再設定のメールのみ、1日あたり数通程度、と書く)。審査には1日ほどかかる

送れなかったときは、ジョブが失敗として記録されます(`docker compose -f compose.prod.yaml logs app` で確認)。

## バックアップ

毎日 午前3時30分(日本時間)に、データベースと画像をまとめて保存します。

- サーバーの中: `/var/backups/recipebook/<日時>/` に7日分(`db.sql.gz`・`storage.tar.gz`・`SHA256SUMS`)
- S3: `.env` に `BACKUP_S3_BUCKET` を書くと、`s3://<バケット>/recipebook/<日時>/` にも送る。30日で消えるように、バケットにライフサイクルルールを付ける
- 含めないもの: キャッシュ・ジョブ・リアルタイム通信用のデータベース(作り直せる)

### 設定(サーバーで1回だけ。リポジトリは /opt/recipebook にある前提)

```sh
sudo cp /opt/recipebook/deploy/backup/recipebook-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now recipebook-backup.timer
systemctl list-timers recipebook-backup.timer      # 次の予定を確かめる
sudo systemctl start recipebook-backup.service     # 今すぐ1回実行して試す
journalctl -u recipebook-backup.service            # 結果を見る
```

S3 に送るには、サーバー(EC2)に IAM ロールを付け、そのバケットへの書き込み(`s3:PutObject`)と、戻すときの読み込み(`s3:GetObject`・`s3:ListBucket`)を許可します。アクセスキーはサーバーに置きません。

### 戻す(リストア)

```sh
cd /opt/recipebook
ls /var/backups/recipebook/                                        # 戻したい日時を選ぶ
sudo deploy/backup/restore.sh /var/backups/recipebook/20261019-033000
# S3 から戻すとき
sudo deploy/backup/restore.sh s3://<バケット>/recipebook/20261019-033000
```

- チェックサムを確かめてから、確認のため `restore` と入力すると始まる
- 戻している間は、アプリと入口(Caddy)を止める(1〜2分)
- 今のデータベースと画像は、バックアップの内容に**置き換わる**(元に戻せない)

このPCで「バックアップ → 全部消す → 戻す」を試し、レシピ・会員・写真が元どおりになることを確かめています。
